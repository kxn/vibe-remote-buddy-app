# UI 设计规范

## 界面文字

- 文字应简明扼要，仅在必须描述功能、状态、操作或后果时出现。能由控件名称和布局表达的内容，不再添加解释。
- 禁止废话、重复提示、教学式旁白；尤其禁止将设计意图、实现策略或开发者自我解释直接暴露在 UI 上。例如「两个入口进入同一向导」「我们会重新核对设备身份」应写在设计文档，不写在产品界面。
- 必须保留影响用户决定的信息：破坏性操作及清除范围、无法撤销的后果、实际故障原因和必要的恢复步骤。简化文字不等于隐藏风险。
- 技术详情按需折叠，不在普通流程中堆叠参数；用于区分目标设备的端口和标识应保留。

## Mock 专用信息

- 临时解释、场景切换器和模拟状态说明统一使用紫色（文字 `#70518f`，背景 `#f0e8f8`），并标注「仅预览」，表示不会出现在成品中。不能只依赖颜色区分。
- Mock 说明独立于产品内容，不混用正常提示、错误或成功的样式；需要解释设计取舍时优先写入配套文档。
- 产品界面中的文字按真实成品标准编写，不因为是 mock 而加入旁白。模拟数据可以展示在真实控件内，由统一「仅预览」说明标明来源。

## 一致性

- 沿用暖色、轻松的现有视觉风格，统一间距和控件样式。
- 任何时候，状态显示及其变化不得影响 UI 布局：加载、保存中、成功、失败、连接和录音状态的出现、消失、文字长度变化或动画，都不得挤动按钮、改变控件位置或使弹窗与页面跳动。状态区预留稳定空间，操作区位置固定；长错误在状态区内滚动或另开详情，不靠撑高布局展示。隐藏的状态与重试入口也必须保留其布局占位。
- 检查和写入期间防止重复提交。验收需比较各状态的控件位置，并覆盖窄窗口、高 DPI 和长错误。
- 适配高 DPI 和窄窗口，必要内容与操作不能被裁切。


## 临时反馈的统一位置

- 普通错误、成功通知、后台进度使用统一底部悬浮反馈区，不插入标题、表单或按钮之间。反馈区脱离文档流，内容限高并可滚动。
- 必须由用户决策或确认的重大问题使用独立弹窗；弹窗内的提示也不得挤动操作区。
- 已有固定状态槽可以原位更新，必须覆盖空状态、长文字、重试按钮、录音播放器及高 DPI；不能只修某一个保存提示。
- 适配、配对、备份、初始化及首页均适用。流程步骤的主动切换与状态文案刷新应区分；后者不能改变布局。

适配流程先验证语音再编辑布局。相同语音键码复用本次试听证明，不在布局中反复准备协议。失效会话属于终止状态，停止轮询并释放录音设备，不得关闭错误后重新弹出同一个错误。

普通底部通知（包括错误）8 秒后自动隐藏，保留手动关闭；父组件轮询刷新不得重置计时。同一挂载通知内容改变时重新计时。接收器选择、进行中的升级等操作或进度须显式保留，不自动关闭确认弹窗。

普通界面文字不可选中，图片和链接不触发浏览器原生拖动；输入框、日志和可复制设备信息保留文本选择。适配布局编辑器的显式拖拽功能保持可用。
